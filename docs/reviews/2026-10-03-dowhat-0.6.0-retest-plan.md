# Fix plan: the DoWhat retest of crumb-kit 0.6.0

Written 2026-10-03 on branch `claude/charming-sagan-9o911q`, at `60ff21b`
(0.6.0 plus the cli.py extraction of health review 2.1, which moved code
without changing behaviour). The report under review is the 0.6.0 retest on
the DoWhat Android project, on Windows 11 under Git Bash. The 0.5.0 retest's
plan, `2026-10-02-dowhat-retest-plan.md`, records what 0.6.0 changed.

## How the claims were checked

- **A replica of the DoWhat clone.** A scratch repository built from the
  `android` eval store plus padding records, about 340 records in all. It was
  cloned the way DoWhat is:
  - shallow (`--depth 141`, one boundary commit);
  - partial (`--filter=blob:limit=1048576`, `remote.origin.promisor=true`);
  - `extensions.worktreeConfig=true` with a `config.worktree`;
  - leftover `REBASE_HEAD` and `ORIG_HEAD`;
  - a handoff written on a cloud branch at a commit four behind HEAD.

  Every guard firing was run in a fresh process with `subprocess.Popen`
  patched to list each `git` process and the call chain that started it.
- **A scratch guard store.** The `android` eval store plus records shaped like
  the report's: the FROM-CACHE attempt, the two tooling attempts, the 429
  attempt citing `known-traps.md`, and 40 padding records so that `test`,
  `results`, `tooling` and `migration` are common words, as they are in a
  402-record store.
- **Speed.** `python -X importtime`, cProfile, and wall time of the real
  entry point. Nothing was measured on Windows; Windows figures below are
  the report's own.

## Corrections to the report

| # | The report said | What the code shows |
|---|---|---|
| 1 | The 5-process firings are probably compound commands or file targets. | They come from the same staleness check as the 2 traced calls. The handoff was written on another branch, so guard also asks git whether `handoff.md` has reached HEAD: `rev-parse --show-prefix`, `ls-tree -r HEAD` and `status --porcelain`. That makes 2 + 3 = 5. The 6 is one more: `rev-list` rebuilding the commit-order cache after HEAD moved. The same 3-process check also runs when a *matched record* was written on another branch, which cloud sessions do (`claude/…` branches). |
| 3 | The hook's reason was "same file(s): known-traps.md". | For `crumb migrate` the reason is "this command writes: .project-memory/known-traps.md" (the writes-file signal), as the report's diagnosis says. "same file(s)" means the action *named* the path; that is item 7's command, not `crumb migrate`. |
| 4 | PLAUSIBLE: the common-word rule demoted `test` and `results`. | **Confirmed, with a second cause.** The record cites `app/build/test-results/` with a trailing slash, and the matcher compared it to the action's `app/build/test-results` as a different path. A trailing-slash path also lost its last name (`test-results`), so not even that matched. With no file match left, only the two words remained, both common, so the record was not topical and its do-not-retry line did not apply. |
| 5b | PLAUSIBLE: `migrate` reaches the `migration` tag through stemming. | **Rejected as stated.** The exclusion runs first: whole crumb segments are dropped from the text before it is split into words and stemmed, so `crumb migrate` never reaches the stemmer. Tags are stemmed, on purpose: a `migrations` tag must meet `migration`. Checking this found a real leak next to it: a crumb command behind a shell keyword or prefix (`do crumb guard …` in a loop, `time crumb --version`) was not recognised as crumb, so its words (`crumb`) stayed and matched `crumb`-tagged records. |

A path in a *quoted argument* is matched by design (`for a in "crumb migrate" ".project-memory/known-traps.md"; do …`), which may be what the command held. |

## New findings

| ID | Finding | Where |
|---|---|---|
| N1 | The `--force` test is a substring test on the whole command, so `uv tool install --force …` is "destructive", and any record that reaches READ_FIRST on it becomes ASK_HUMAN. ## Issue by issue

Each item: the cause, the fix, and the test that fails at `60ff21b` and
passes after.

**1. Git processes on every guard firing.** Cause above (corrections, 1).
- **Fix:**
  - The hook no longer computes staleness at all. It never shows it: the
    hook's reason lists matched records only. `crumb guard` still reports
    staleness.
  - "Has this record file reached HEAD?" no longer starts git at a stable
    HEAD. The store's part of HEAD's tree (path and blob id) is cached in
    `index/` per HEAD, like `commit-order.txt`. A file has reached HEAD when
    its bytes hash to that blob id (CRLF folded to LF first, as git does).
    One `git ls-tree` per new HEAD, only when a record on another branch is
    matched.
  - The work-tree root is found from `.git` on disk, so `rev-parse
    --show-prefix` is not needed either.
- **Layout check:** on the replica (shallow, partial, worktreeConfig,
  leftovers), with the origin removed so any fetch would fail, a firing at a
  stable HEAD starts 0 processes. After HEAD moves, at most 2 (`rev-list`,
  `ls-tree`), neither of which needs a blob or the network.
- **Tests:** a full guard firing at a stable HEAD starts 0 git processes
  when (a) the handoff names a commit and another branch, and (b) a matched
  record was written on another branch. Both start 5 / 3 today. A test on a
  real shallow, blob-filtered clone with the DoWhat layout.

**2. Start-up cost.** Profile on Linux, the hook's own entry point:

| Phase | Linux | Windows (report) |
|---|---|---|
| Python start (`-c pass`) | 16 ms | ~102 ms |
| `import breadcrumbs.cli` and friends | ~77 ms | 48 ms (`import_ms`) + console-script launcher |
| Guard work, 5 git calls included | ~45 ms | ~215 ms |

- `dataclasses` is imported by four hook-path modules for five small
  classes. It pulls in `inspect`, `ast`, `dis`, `tokenize` and `linecache`:
  about 10 ms on Linux. `typing` (4 ms) is imported only for annotations.
  `subprocess` (6 ms) is imported even when no git process runs.
- **Fix:** plain classes in place of the dataclasses on the hook path,
  annotation-only `typing` imports moved under `TYPE_CHECKING`, and
  `subprocess` imported when a git process is actually started.
- **Test:** `crumb hook guard`, run as the hook runs it, imports none of
  `dataclasses`, `inspect`, `ast`, `typing` or `subprocess`.
- **DECIDE (launcher):** tradeoffs are in the reply to the report, not
  decided here.

**3. crumb's generated files count as files the command writes.**
- **Fix:** crumb's generated files (`known-traps.md`, `open-questions.md`,
  `generated/`, `index/`) are memory, not a subject. They are dropped from
  the files a crumb command writes, and from a record's cited files. A
  trap's own `--area` still counts, because there the author named the file
  as the subject.
- **Test:** an attempt citing `.project-memory/known-traps.md` is not cited
  by `crumb migrate`, `crumb reindex` or `crumb note trap`.

**4. The exact do-not-retry attempt became advisory.**
- **Fix:**
  - A trailing slash no longer makes a different path.
  - A path the action names and the record cites (in its evidence or its
    prose) makes the record topical, and an objection, whatever the words.
- **Test:** the FROM-CACHE attempt, citing `app/build/test-results/`, is
  blocking for `rm -rf app/build/test-results`, in a store where `test` and
  `results` are common. Also with the path only in its prose.

**5. Records on nearly everything.**
- (a) **Fix:** an objection needs evidence about *this* action. The
  do-not-retry line now applies only when the record shares with the action:
  - a file (named, written, or cited in prose and named by the action);
  - its exact command;
  - two rare words of its *title* beyond its tags;
  - or a rare tag plus a rare title word plus two rare words beyond its tags.

  A tag plus a few words from the body is still a match, and it may still be
  READ_FIRST, but it is not an objection.
- (b) **Fix:** a crumb command behind a shell keyword or prefix (`do`,
  `then`, `else`, `if`, `while`, `until`, `!`, `{`, `(`, `time`, `nohup`,
  `command`, `exec`) is recognised as crumb.
- **Tests:** the two tooling attempts are not blocking on the timing command
  or on `uv tool install …`; the MigrationV21ToV22Test attempt is not
  blocking on the heredoc command; `do crumb guard "$a"` contributes no
  words.

**6. `rm -f` of a temp file asks the human.** Cause: `rm` classes as a
deletion, and a deletion turns any READ_FIRST into ASK_HUMAN.
- **Fix:** a segment that only deletes scratch files is not a deletion.
  Scratch means under the system temp directory (`$TEMP`, `$TMP`,
  `$TMPDIR`, `${TMPDIR:-…}`, `%TEMP%`, `/tmp`, `/var/tmp`, a `…/Temp/`
  folder) or created earlier in the same command (`cp`/`mv` destination,
  `touch`, `tee`, an output redirect). `rm -rf` outside build, cache and
  temp directories stays high-impact.
- **Tests:** the report's command is not ASK_HUMAN; `rm -f "$TEMP/x"` is
  routine; `rm -rf src` and `rm -f src/main.kt` still count as deletions.

**7. Heredoc text in the verdict.**
- **Fix:** the destructive-shape check reads the command without data
  heredoc bodies. A heredoc fed to a shell or a database client (`bash`,
  `sh`, `zsh`, `ssh`, `psql`, `mysql`, `sqlite3`, …) is code and still
  counts. One fed to `while read`, `cat >`, `python -` or `tee` is data.
- **Test:** the report's loop is not ASK_HUMAN; `bash <<'EOF'` holding
  `git push --force origin main` still is destructive.

**8. A 10.2 s Stop firing.** Measured on the replica: a Stop firing that
writes a snapshot takes 1.1 s at 200 records and 1.6 s at 340 records on
Linux. Almost all of it is the projection rebuild after the record is
written, plus a whole-store `validate` of the new file. With the report's
Linux-to-Windows ratio for guard (about 4–5×), a snapshot on a 400-record
store takes 6–10 s on Windows. Redundant firings (nothing moved) take
milliseconds, which is the 287 ms median. Mining is bounded at 8 MB a
firing.
- **Bounded here:** the hook log now records `mine_ms` and `snapshot_ms`
  for each Stop firing, so the next slow firing says which it was.
- **Not moved off the hook path here:** see *Not fixed*.
- **Test:** a snapshot firing's log line carries both timings.

**9. uv's cached index.** README: `--refresh-package crumb-kit` in the uv
install and upgrade commands, with the reason.

## Not fixed (proposals)

- **N1, `--force`:** read it per command (`git push`, `git clean`,
  `git checkout`, `git branch`, `rm`), not anywhere in the line.
- **Item 8, moving the snapshot's publication off Stop:** write the session
  record in the hook and let a detached `crumb reindex` publish. The cost: for
  the seconds it runs, `validate` reports a stale projection and guard has no
  verified pre-filter.
